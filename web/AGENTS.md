# Prototype Instructions

## Current product direction

- This is a desktop-first HTML game for MCU circuit learning, from beginner to professional levels.
- Keep levels data driven. Put per-level title, story, parts, initial positions, wiring goals, electrical values and declarative objective conditions in `src/levels/`; keep drag, wiring, probe and result UI shared. New levels that reuse an existing component/model family must be added by configuration only. Add a new component renderer or electrical model once per reusable family, not once per level. Follow `LEVEL_ARCHITECTURE.md` and validate level data before it reaches the runtime.
- The former level 32 is now level 1. The prior levels 2–5 were merged into one exploratory first level: players choose a resistor, reverse the LED, compare probe readings and current flow on the same board. Do not split these variations into repetitive levels. Future distinct circuits can still be added through the level catalog.
- Use the selected dark game UI image at `../assets/ui-concept-game-dark.png` as the visual reference.
- Keep the interface comfortable for long sessions: low-glare blue-green surfaces, restrained amber rewards, clear electrical readouts, and enough contrast for circuit work.
- Make levels feel like an engineering puzzle through progress, objectives, and immediate electrical feedback. Do not show star grades or XP; a future level may unlock a component instead.
- Component illustration assets will be drawn later. Current schematic and inventory visuals are functional simplified representations.
- On a failed simulation, show a clear result flow with the observed behavior, cause, and a path to edit or retry. Distinguish open circuits, reversed LED, shorts, and a direct LED path without current limiting. Do not claim that a real LED always burns; label dramatic damage feedback as a teaching model.
- Level 1 has a player-selected resistor. Show the Ohm's-law method and necessary parameters in the resistor menu, but do not show precomputed answers or a result table for the candidate values. Keep live electrical feedback and probe readings after a choice. Do not restore the old "目标接法 · 电流推演" panel. Treat the 20 mA line as this level's teaching threshold rather than a universal component rating.
- Clicking a component in the inventory opens its parameter/info menu without placing it. Physical parts and the probe are placed by dragging into the board with Pointer Events and pointer capture; avoid native HTML drag and drop, which left Safari without a matching pointer-up event after inventory placement. Keep inventory tiles compact (about half the earlier tile footprint) and use recognizable resistor, electrical ground, and test-probe symbols. A placed component opens its anchored parameter menu only on pointer release after an actual click; dragging it and releasing must leave the menu closed. Position the menu fully outside that component's visual bounds so the player can immediately drag the same component again without first clicking the empty board. Fixed components display their fixed parameters without invented choices.
- Animate short moving marks along each modeled conducting path in the conventional-current direction, even when the level objective is not met. For example, a powered GPIO0 → 330 Ω resistor → GND branch without an LED carries about 10 mA and must show flow while the LED goal stays incomplete. Do not invent steady current in an open, reversed, or unquantified fault path; honor reduced-motion settings.
- Open levels with an entirely empty board: MCU, power, GND, resistor, LED, probe, and wires all begin unplaced. Keep the contextual edit menu available after component click, including delete and LED reverse.
- Electrical state, LED appearance, current animation, probe readings, scope traces, and goal checks update continuously as the player edits the circuit. An optional inspect action may explain an incomplete or unsafe circuit; it must not gate the live results.
- The probe must move between terminals and wires and drive the scope's point label, numeric voltage, waveform, and inferred branch current from the same live level model. Show 0 mA where no modeled conducting path passes, and an indeterminate reading for faults the model cannot quantify. Explain that current is a branch estimate, not a physical single-point voltage-probe measurement. Never present a floating or faulted node as a measured zero volts; moving a component without changing its wires must keep its electrical result and attached probe in sync. Show LED condition directly on the board instead of in a separate status card.
- Treat each reusable physical component as an entity with a derived state object from the shared electrical report. LED brightness follows the modeled LED branch current continuously, including when goals are incomplete; dark and failed states have zero glow. Resistors distinguish normal, conducting and power-overload burst states. Compare resistor dissipation P = I²R with that resistor's configured wattage; the 20 mA teaching comparison is not a damage threshold. Label burst effects as teaching visuals, since real failure depends on the part and conditions.
- When the user checks a completed circuit, open a distinct level-clear dialog with a restrained celebration effect and the key electrical measurements. Keep live goal checks independent of that dialog. Do not introduce star grades or XP.
- Placing a probe must leave endpoint clicks in wiring mode so it never blocks circuit construction. The probe handle can always be dragged for a measurement; use a distinct, explicit measurement control when endpoint clicks should reposition it.
- Movable components snap to the same hole-grid coordinates used to draw the board background, including drag-and-drop placement and zoomed views.
- When a wire connects to a right-side terminal, keep its first segment leaving that terminal to the right even if the other component is placed farther left. Route around the component bodies, and use the same physical route in reverse for current animation and probe snapping regardless of which endpoint the player selected first.

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.
