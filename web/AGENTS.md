# Prototype Instructions

> 仓库级约定见 [../AGENTS.md](../AGENTS.md)：其中规定 **未经用户明确命令不得执行任何写类 git 操作**（commit / push / checkout / stash 等）。本文件只覆盖 `web/` 原型自身的约定。

## Current product direction

- This is a desktop-first HTML game for MCU circuit learning, from beginner to professional levels.
- Keep levels data driven. Put per-level title, story, parts, initial positions, wiring goals, electrical values and declarative objective conditions in `src/levels/`; keep drag, wiring, probe and result UI shared. New levels that reuse an existing component/model family must be added by configuration only. Add a new component renderer or electrical model once per reusable family, not once per level. Follow `LEVEL_ARCHITECTURE.md` and validate level data before it reaches the runtime.
- **第 1 章正在重建为 3 关**（用户决定：前 8 关压缩为 3 关，面向大学生，不再重复高中内容）。旧的「分流节点 / 分流支路 / 双源供电」三关全部作废重建；高中已覆盖的欧姆定律、串并联、分压分流、电功率大小、闭合电路欧姆定律不再单独设关，只作为这三关里随手要用的工具。规格表见 `../课程与关卡蓝图.md` 的「第 1 章 3 关（重建）」：① **参考方向与功率**（已实现） —— 12 V 电源经 R1 供电、R2 接地的节点 A 上再接一只 6 mA 电流源，玩家选值并决定它接在 A–GND 之间的方向，让节点 A ≈ 3.0 V；此时电流源端电压 −3 V、在**吸收** 18 mW（源也可能被充电），目标之一是按板上画出的参考方向判断三个元件的吸收/释放。参照解 R1 = R2 = 1 kΩ：9 mA / 3 mA / 6 mA，功率 108 = 81 + 9 + 18 mW。② **源与受控源**（已实现）—— 两级分压链 9 V → R1 → 节点 A → R2 → 节点 B → R3 → GND，压控电流源按 g·U_B 注入节点 A（控制量取节点 B），g **由玩家用滑块整定**：默认 0.25 mS、参考 0.5 mS。目标 ① 节点 B ≈ 3.6 V ② 受控源输出 ≈ 1.8 mA；参考解三只电阻都是 1 kΩ + g = 0.5 mS → U_A = 7.2 V、U_B = 3.6 V、I = 1.8 mA（g 与阻值都必须对，默认值 1.5 k/1 k/1.5 k 落在 3.93 V）。这一关的**新操作是整定**（元件菜单里的跨导滑块，`game.controlledGmMs`，`electrical.gainRangeMs` 给范围），不再只是"拖电阻 + 选值"。`circuit.controlledSource` 声明流出/流回端与控制量的两个端点，`electrical.controlledTransconductanceMs` 给参考 g、`defaultTransconductanceMs` 给开局 g；求解器把 g·U控制 作为含未知量的项放进节点方程（`controlledSourceCurrentMa`、`controlledSourceControlV`、`controlledTransconductanceMs`），受控源只在自身回路闭合且控制支路接到参考节点时才输出，控制量为 0 就输出 0——它不能独立激励。第一版只做压控型。③ **功率预算与供电设计**（已实现，**自由搭建 + 选器件档位**）—— 12 V 电源给固定的 100 Ω 负载供电，目标 ① 节点 A（负载电压）≈ 3.0 V ② 负载功率 ≈ 90 mW。串联部分由玩家自己拖电阻、接线、选值；**每只电阻还能选额定功率档位**（`electrical.resistorRatingOptionsW: [0.25, 0.5]`，默认 `resistorRatedPowerW`），元件菜单里是一排 250 / 500 mW 按钮，板上标签也写着 `R1 · 600 Ω · 250 mW`。串联部分要吃掉 9 V、通过 30 mA，等效阻值必须是 300 Ω：一只 300 Ω 独自扛 30 mA 就是 270 mW，¼ W 器件超限；两条出路——把额定功率换成 ½ W，或者用两只 600 Ω 并联让电流各半（每只 135 mW）。三条路都合格，取舍在件数、裕量与成本。判题仍是两条读数；器件应力由实时反馈拦下，过载文案按**每只器件自己的额定值**报「R1 270 mW / 250 mW（实际 / 额定）」并给出两条降应力思路。
- **额定额定功率是每只器件自己的属性**：求解器在 `resistorResults[id].ratedPowerW` 上报（`game.resistorRatings[id] ?? electrical.resistorRatedPowerW`），过载判定、元件状态、状态文案、板上标签和「查看答案」的参考取值都读它；`defineLevel` 校验档位列表包含默认值。以后任何"器件额定值"教学都走这条通道，不要再写死成关卡级常量。
- **判定弹窗只能由「检查电路」触发**（`src/faultPolicy.js`）：`autoInspectKinds` 只保留会真正让电路失效的故障（`overcurrent`、`gpio-short`、`supply-short`、`current-source-short`），**`resistor-overload` 不再自动弹窗**——器件超过额定值是玩家在第 3 关搭建过程中必然会遇到的中间状态，自动弹窗等于替玩家按了检查电路、还打断搭建。过载要能实时看见（元件变红、状态栏报「功率超限 · 270 mW / 额定 250 mW」），完整解释留给按钮。新增故障类型时先想清楚它属于"状态"还是"电路已失效"。
- **不要做多选题**（用户否决，2025）：第 3 关一度做成"左侧候选方案里选一个"，理由是只换方案就能穷举、实时勾选等于送答案。但用户的判断是**选择题缺乏游戏性**——这个游戏的核心操作是拖动、接线、看读数。该实现（`levelCandidates.js`、`circuit.candidates`、候选面板、`verified` 延迟判定）已全部删除；不要把"多点一下选一个"当作新操作，需要的操作感要来自拖动/接线/整定/测量本身。取舍要落在**玩家自己搭出来的电路**上（例如同一只 300 Ω：选 ½ W 器件还是拆成两只 ¼ W 并联）。
- **每关的答题步骤不能雷同（用户硬性要求，见 `../课程与关卡蓝图.md` 难度规则 9）**。相邻关卡不得使用同一套操作序列；每关必须写明**主要动词**——搭建 / 判断 / 整定 / 预测 / 测绘 / 取舍 / 归并 之一或组合——以及每一步动的是哪个量，并登记在蓝图的「答题步骤对照」表里。复用上一关的动词时，必须同时增加一个**新操作**。已实现与在做的对照：第 1 关＝搭建 + 判断（放两只电阻、决定电流源方向、逐只元件判断吸收/释放）；第 2 关＝搭建 + 整定（三只电阻接成两级分压链，再拖跨导滑块把节点 B 与受控源输出同时调到目标）；**第 3 关是自由搭建 + 选器件档位**（自己拖电阻接线，但每只电阻还要选 ¼ W / ½ W 额定功率档位——同一个 300 Ω 既可以换大额定值，也可以拆成两只并联分流），它与第 1、2 关的差别在「要动的是器件参数与拓扑，而不只是阻值」。新增关卡时先写出步骤设计，再写知识点；只换知识点、不换步骤的关卡不予立项。
- 关卡可以命名**第二个节点**（`circuit.nodeB` + `nodeBV` 读数 + 画布上的节点 B 符号），用于两级分压这类中间点；探针与元件菜单都按节点名标注。判定"支路断开"要看**两端是否都在参考岛上**（求解器给每个电阻 `connected`），不能只看电流为 0：把节点抬到电源电位时某只电阻本来就可能没有电流。
- **长列表必须能滚，不能裁掉内容**：右栏的知识卡面板吃掉剩余高度并在面板内部滚动（`.right-stack > .knowledge-panel { flex: 1 1 auto; min-height: 148px; overflow-y: auto }`），标题用 `position: sticky` 固定；其余面板 `flex: 0 0 auto`，窗口太矮时由左右两栏自身滚动。滚动容器加 `overscroll-behavior: contain`，并给 WebKit 补 `::-webkit-scrollbar` 样式（`scrollbar-width/color` 只管 Firefox）。新增面板或卡片列表时照此办理，不要用 `overflow: hidden` 把内容裁掉。
- 元件菜单除了选阻值，还可以放**连续整定控件**（目前是压控源的跨导滑块 `onTuneGain`）和**菜单内的判定按钮**（第 1 关的吸收/释放）。这类控件实时改写游戏状态并让读数跟着动，参考解仍由 `startGame(true, level)` 给出。**关键约定：`updateGame` 默认会 `setSelected(null)` 关掉元件菜单（放置、接线、删除后关菜单是对的），所以菜单内的控件必须传 `{ keepSelection: true }`，连续拖动还要传 `{ coalesce: true }` 把整次拖动并成一步撤销**——否则滑块一动菜单就消失，玩家根本拖不动（真实踩过的坑）。
- 重建时 **6 mA 电流源「反接」在第 1 关是合法接法**（那正是让源吸收功率的正解），不是故障；「反接即错误」只属于具体关卡，不能写进通用运行时。第 1 章也不再需要「电流源没接到节点 A」那类提示。
- **参考方向按板上约定直接画出**（电源从 + 端流出、电流源从流出端流出、电阻 a → b），玩家据此判断吸收/释放；第一版不做「翻转参考方向」控件。判题需要**每个元件带符号的功率**（吸收为正），元件状态与通关弹窗的功率读数都从它来。
- 第一版受控源只做**压控**型（VCCS/VCVS）：它可以直接进入节点法方程。流控源需要支路电流作为未知量（MNA），留到第 4 章再实现。
- 本文件下面凡是指明「第 1 关 / 第 2 关 / 第 3 关」具体规格的段落（预设三只电阻、6 mA 并联分流、双源共节点等）都随本次重建作废；其中与具体关卡无关的通用约定（交互、探针、路由、缓存、组件族解析、无故障注入题型、每关目标上限）继续有效。
- **「查看答案」按钮**（搭建区底部，撤销/重置旁）打开的是从关卡数据算出来的参考解，不是硬编码文案：`src/levelAnswer.js` 用 `startGame(true, level)` 解出参考接法（`circuit.solutionWires` 逐条翻译成人话，节点 B 与受控源也要有名有姓）、参考取值（`electrical.referenceOhms` **加上一切可调参数**，例如「跨导 g = 0.50 mS（当前 0.25 mS）」——只列电阻值会让人以为照着摆就对，这是真实踩过的坑）、参考读数与各元件带符号功率，并对含 `powerJudged` 的关卡列出判断答案。新增关卡只要声明参考解就自动有答案页；不要为某一关写专门的答案文案。答案页要在明处说明「任何满足目标读数的等效接法同样合格」，并引导玩家重置后自己重搭。
- Every level lists **at most two task goals**. A goal is either an electrical reading or a judgement/prediction conclusion (user decision: the rebuild of chapter 1 needs concept goals such as "judge whether each element absorbs or delivers power"); an instrument's position is still never a goal. Prefer two single-reading goals over one long compound sentence, so the checklist can say which half is off. The probe is a measuring tool, not an objective: where it sits, or whether it is placed at all, must never change the verdict (`probeOnNodeA` was removed for exactly this reason; only the legacy LED template's explicit `measurement` step still uses `probeAt`). Safety, per-resistor power, extra node voltages and source terminal readings belong to live feedback and the level-clear dialog, not to the goal list; a fault verdict (short, open loop, unselected part, bypassed part, overload) reports `success: false` **and blanks the checklist**, because a broken build is not a valid answer yet — otherwise two readings that coincide with the target values (level 3: a bare 1 kΩ/2 kΩ divider already reads 6.00 V and 3.00 mA) would light both goals while 检查电路 rejects the circuit. Only `target-mismatch` keeps its real checklist, since that is the case where the ticks show what is still missing. Do not grow the goal list beyond two — teach more with the story, the failure feedback and the knowledge cards.
- Abandoned game type (user decision, do not revive): hiding an open wire or a shorted component and asking the player to locate it by measurement. It taught only the measurement ritual and little new knowledge, so it is removed from the catalog, the roadmap and the code (`hiddenOpenCandidates`, `hiddenShortCandidates`, `suspectedWires`/`suspectedShort`, and the diagnosis branches in `App.jsx`, `CircuitBoard.jsx`, `goalRules.js`, `defineLevel.js`). Fault classification remains as live feedback for the player's own miswiring: open branch, source short, current-source short, reversed current source, bypassed resistor, power overload. Carry new knowledge with new circuit structures per level instead of fault injection.
- Historical prototype: the former level 32 was a GPIO–resistor–LED level 1, merging several LED variations into one exploratory level. Its reusable circuit model remains available outside the active level catalog and can later be adapted for the semiconductor or MCU chapter. Do not split those variations into repetitive levels.

Students can drag them onto the board immediately and change their values afterward by clicking the placed parts; selecting a value before placement is optional. The defaults should not solve the level. Clear the level from the constructed circuit, an actual probe reading at midpoint A, and live electrical measurements without requiring typed calculations. Explain current, voltage relative to GND, Ohm's law, equal series current, voltage drops and power without precomputing every choice. Keep live feedback and probe readings after every choice. Do not restore the old "目标接法 · 电流推演" panel or the manual "计算验算" input panel.
- Clicking a component in the inventory opens its parameter/info menu without placing it. Physical parts and the probe are placed by dragging into the board with Pointer Events and pointer capture; avoid native HTML drag and drop, which left Safari without a matching pointer-up event after inventory placement. Keep inventory tiles compact (about half the earlier tile footprint) and use recognizable resistor, electrical ground, and test-probe symbols. A placed component opens its anchored parameter menu only on pointer release after an actual click; dragging it and releasing must leave the menu closed. Position the menu fully outside that component's visual bounds so the player can immediately drag the same component again without first clicking the empty board. Fixed components display their fixed parameters without invented choices.
- Animate short moving marks along each modeled conducting branch in the conventional-current direction, even when the level objective is not met. Do not invent steady current in an open or unquantified fault path; honor reduced-motion settings.
- In level 1, pre-place and fix the source, visibly labeled node A, and GND on the board. Students place and choose R1 and R2, wire them in series through A, and measure the result. Fixed reference points must survive reset and cannot be moved or removed. Keep the contextual edit menu available after movable component click, including value changes and deletion; later LED levels also support reversing polarity.
- Electrical state, component appearance, current animation, probe readings, scope traces, and goal checks update continuously as the player edits the circuit. An optional inspect action may explain an incomplete or unsafe circuit; it must not gate the live results.
- The probe must move between terminals and wires and drive the scope's point label, numeric voltage, waveform, and inferred branch current from the same live level model. Show 0 mA where no modeled conducting path passes, and an indeterminate reading for faults the model cannot quantify. Explain that current is a branch estimate, not a physical single-point voltage-probe measurement. Never present a floating or faulted node as a measured zero volts; moving a component without changing its wires must keep its electrical result and attached probe in sync. Show LED condition directly on the board instead of in a separate status card.
- Treat each reusable physical component as an entity with a derived state object from the shared electrical report. In active level 1, each resistor distinguishes normal, conducting and power-overload states using its own P = I²R and rated power. Later LED brightness should follow its modeled branch current continuously; any burst visual is a teaching effect, since real failure depends on the part and conditions.
- When the user checks a completed circuit, open a distinct level-clear dialog with a restrained celebration effect and the key electrical measurements. Keep live goal checks independent of that dialog. Do not introduce star grades or XP.
- There is no wire/measure mode switch: the header's 连线 and 测量 buttons were removed (user decision — they only toggled whether an endpoint click also moved the probe, while a probe grip drag already did that). Endpoint clicks always start or finish a wire, so circuit construction can never be blocked by measurement; the probe is repositioned by dragging its grip (or with the arrow keys while it is focused) and clicking it opens its parameter menu. Do not reintroduce a modal mode toggle for the probe.
- Connect wires by pressing one terminal, dragging to another terminal with a live following wire preview, and releasing there. A plain sequence of terminal clicks must not create a wire; releasing away from a terminal cancels the preview. Keep keyboard terminal access available.
- Movable components snap to the same hole-grid coordinates used to draw the board background, including drag-and-drop placement and zoomed views.
- Wire routing lives in `src/circuitGeometry.js` (`componentObstacles` → `wireRoute` → `createRouteResolver`). The contract, all of it covered by tests: strokes are orthogonal; **every side terminal leaves and is reached from its own side** (a left terminal from the left, a right terminal from the right, even when the other component sits on the opposite side) with an 8px direction stub; crossing the wire's own endpoint body on that stub is free (a wire starts on its terminal) while every later segment still pays full price, which is what forbids folding back over a symbol; a stroke must **never enter any placed component's `visualBounds` box** (weight 1000000/px) while the surrounding 14px clearance ring only costs half a point per pixel — a tie-breaker between equally direct routes, never a reason to detour, so on crowded sandbox boards a wire grazes a ring rather than clipping a symbol or swinging around it. A wire always reaches its terminals with the fewest bends the side rules allow: on an unobstructed board every stroke is Manhattan-minimal (measured slack 0 on the reference circuit). Corridors come from the board frame, every component's box and clearance edges and the terminal stubs; a two-segment candidate is used when it is clear and a Dijkstra grid search takes over when it is not; endpoint coordinates are never filtered out, so a terminal in the board corner still routes. Wires also avoid each other: two strokes that cross read as a junction even though they are not connected, so a crossing costs 20000 points and being drawn on top of another wire costs 60 points per pixel. Both are errors rather than tie-breakers: one crossing is dearer than any detour the board can express, so a wire walks around the board instead of over another wire whenever a clear route exists, while one pixel of ink still outranks them all. A stroke never avoids itself. `createRouteResolver` resolves this by relaxation so no route depends on the order wires were created: every wire is first routed clear of components only, then re-routed against the others' current routes, repeating (at most 4 rounds, and only the wires that actually cross) until the board is calm or the count stops improving; the calmest round is kept. The map is keyed by the normalised wire key (so either drag direction finds the same stored route and is answered in the right orientation) and a stored route is handed back verbatim rather than recomputed — recomputing with the whole set as neighbours made a wire dodge itself. Crossing work is filtered by bounding box per candidate and per segment. Measured on 300 randomly placed level-3 boards whose parts do not overlap: 84% route with no crossing at all, and the 流回 wire is involved in 3%; the unfiltered sandbox sample (parts allowed to sit on each other, where a terminal can be buried under another symbol) still improves from 759 to 260 crossing pairs. The crossings that remain are geometric — the side rules plus the symbols' own ink leave no single-layer path — which is the same reason a real board needs a via. Because a bare crossing still *reads* as a junction, `crossingHops()` marks every remaining intersection and `routePathWithHops()` draws it as a small semicircular hop on the wire whose normalised key sorts later (so both wires agree, whatever order they were created in); the stroke, the moving current marks and the hit area all use that path. **Never draw a bare crossing.** Cold routing on a 24-part / 48-wire board is ~0.6s and every later pass ~1ms. The committed wire, the drag preview while hovering a terminal, the current animation and probe snapping must all resolve to the same polyline regardless of which endpoint the player selected first. Routes are cached per geometry fingerprint plus the sorted wire list (that is the invalidation key: place, delete or move any part, or add/remove a wire, and the affected routes recompute). Do not reintroduce a router that only special-cases the right side, picks a corridor from the two endpoints alone, or treats the clearance ring and the symbol box as equally bad — those are exactly what let wires run through components.
- Resolve every component shape through `componentSpec(id)` in `src/componentCatalog.js`, never a raw `componentCatalog[id]` lookup. Every library the player can drop without a count limit is declared once in the `dynamicFamilies` table (`r\d+` today; a capacitor family would be one more row) and every instance id then works like the first: geometry, snapping, probe, routing, level validation and the electrical model. Level 1 history lesson: the sandbox fix for level 1 only extended a hardcoded `r1`–`r4` list, so level 2 broke again on the fifth resistor — `componentCatalog[id]` returned nothing, `pinPosition` returned `null`, and the first wire to touch it threw during render and blanked the whole board. Geometry and probe code must skip an unknown or unplaced shape instead of assuming it exists, and `nextResistorId` is the single source of truth for naming a newly dropped part.
